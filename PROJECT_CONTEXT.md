## 1. Project Overview

Browser-based Android device inspector using **WebUSB + ADB protocol**. Runs 100% client-side — no server, no ADB installed on host. Now also supports **remote-shared sessions** (see §13): a second user, anywhere, with just a browser, can view live device status and run approved shell commands against the host's physically-connected device via WebRTC.

## 3. USB/ADB Connection Flow

### 3.1 Initial connection (new device via +Connect Device button)
1. Click `+Connect Device` → `scanDevices()` (line 95)
2. `AdbDaemonWebUsbDeviceManager.BROWSER.requestDevice()` shows browser picker
3. User selects device → returns `USBDevice`
4. Calls `connectDevice(usbDevice)` (line 236)

### 3.2 connectDevice(usbDevice) — line 236
The MASTER connection function. ALL paths converge here:
1. Validates `usbDevice` has `.connect()` method
2. `usbDevice.connect()` — opens USB connection
3. `AdbDaemonTransport.authenticate()` — establishes ADB protocol
4. `new Adb(transport)` — creates ADB client
5. Reads `ro.serialno` to get actual ADB serial (may differ from USB serial)
6. Sets up `USBConnection.closed` listener for disconnect detection
7. Sets up heartbeat (3s interval, `adb.getProp('ro.build.id')`)
8. Registers `_usbDisconnectHandler` on `navigator.usb` (one-time, line 334)
9. Stores in `connectedDevices` Map
10. Calls `renderDeviceList()` + `selectDevice(adbSerial)`

### 3.3 Reconnecting from "Ready to Connect" list — connectAvailable() line 547
TWO-STEP strategy:
1. **Instant reconnect**: `navigator.usb.getDevices()` → find matching device by `_usbId` → pass directly to `connectDevice()`. No picker needed.
2. **Fallback picker**: If device not in `getDevices()` (was unplugged and re-plugged), use `mgr.requestDevice()` to show picker, then `connectDevice()`.

**CRITICAL**: Do NOT pass the raw USBDevice to `AdbDaemonTransport.authenticate()` — you need `usbDevice.connect()` first, which returns a `USBConnection`. `connectDevice()` handles this. The v1.1.41 bug (`pipeTo` error) was caused by passing the USBDevice directly as `connection` to authenticate.

### 3.4 Disconnect via button — disconnectOne() line 587
1. Calls `transport.close()`
2. Deletes from `connectedDevices`
3. Moves device info to `availableDevices` (keeps it in "Ready to Connect")
4. Key format must match `scanAvailableDevices()` — uses `serial || vid:pid:timestamp`

### 3.5 Physical unplug — _usbDisconnectHandler line 334
Registered ONCE on `navigator.usb.addEventListener('disconnect', ...)`:
1. Event fires with `e.device` (the unplugged USBDevice)
2. Matches against `connectedDevices` using `_usbId` (serial preferred, fallback to vid+pid)
3. If matched in connected: close transport, delete from connected, delete from available
4. If matched in available only: delete from available
5. Calls `renderDeviceList()` to update UI

### 3.6 USB connect events
- `navigator.usb.addEventListener('connect', scanAvailableDevices)` — line 73
- Also called on page init with 500ms delay — line 68

### 3.7 scanAvailableDevices() — line 123
1. `navigator.usb.getDevices()` gets all previously granted devices
2. Builds `knownConnected` and `knownAvailable` sets using `vid:pid:serial` keys
3. Skips devices already in connected or available
4. Adds new devices to `availableDevices` Map
5. Calls `renderDeviceList()`

## 7. Known Bugs and Fixes

### v1.25.1 — long screenshot froze the host tab ("not responsive")
Real report right after v1.25.0 shipped: the plain Screenshot button worked, but Long Screenshot made the host tab unresponsive. Root cause: `findScrollOverlap()`'s first version ran its sliding-strip search directly on the FULL-RESOLUTION frames and called `getImageData()` once per candidate row — roughly 300+ calls per frame transition, each pulling a full-device-width strip off the canvas, entirely synchronously with no `await`/yield point anywhere in the loop. Multiplied by up to `LONG_SCREENSHOT_MAX_FRAMES` (15) frame transitions, this blocked the host tab's main thread for long enough to look and behave frozen — no UI response, and likely delayed the tab's own WebRTC/relay message handling too, since JS is single-threaded and nothing else could run while this loop did.

Fixed by downscaling before searching instead of after: both frames get reduced to a ~150px-wide proxy first (two cheap `getImageData()` calls total, one per frame, instead of ~300+), the entire sliding-strip search runs on that tiny in-memory pixel buffer (plain array reads, no further canvas calls), and the found offset is scaled back up to full-resolution coordinates for the actual stitch. Also added an explicit `setTimeout(...,0)` yield between the overlap search and the next canvas draw per frame, as cheap insurance on top of the real fix. No behavior/output change — same alignment algorithm, same fallback-on-poor-match logic, just ~2-3 orders of magnitude less work per frame transition.

### v1.25.0 — Long (scrolling) screenshot in Remote Control (not a bug fix)
Requested: "is it possible to take a long screenshot (scroll to the end of the page)?" Android/ADB has no generic long-screenshot API — it's an OEM system-UI feature (Samsung/Xiaomi/etc.), not something `adb shell` exposes — so this is built at the app level instead: `handleLongScreenshotRequest()` (host) captures a frame, swipes up one "page" (`input swipe`, from 85% to 15% of screen height), captures again, and repeats up to `LONG_SCREENSHOT_MAX_FRAMES` (15) or until a swipe stops producing new content (treated as "reached the bottom"). Each new frame is stitched onto the growing image by `findScrollOverlap()`, which slides a thin strip from the previous frame's bottom edge through the new frame's upper-to-middle region to find where it re-appears (a bounded template-match, not a fixed pixel offset — different apps/pages don't scroll the same amount per swipe) and only appends the portion below that match. Falls back to a fixed ~15% overlap if no good match is found (page changed unpredictably between frames). Bounded by an overall `LONG_SCREENSHOT_TOTAL_TIMEOUT_MS` (100s) wall-clock cap in addition to the frame-count cap.

New actions: `longScreenshotRequest`/`longScreenshotResult` (viewer↔host, `requestId`-based dedup like `screenshotRequest`/`screenshotResult`) and `longScreenshotProgress` (host→viewer, status text only — deliberately carries **no** `requestId`, since it fires many times per operation and `deliver()`'s dedup keys on `(action, requestId)`; reusing one `requestId` across every progress message would make every one after the first look like an already-seen duplicate and get silently dropped). Same authorization model as the existing single-frame Screenshot button and every other control action: must currently hold the control grant for that device (`isController()`), no separate approval step. UI: a "Long Screenshot" button next to the existing "Screenshot" button in the Remote Control tab's hardware-buttons row, reusing the same status badge (`#control-apk-status`) for progress text.

**Known limitation, by nature of the approach**: sticky headers/footers, ads, video, or any content that changes on its own between frames (not just because of the scroll) can produce a misaligned or duplicated seam in the stitched result — this isn't a bug to fix, it's the inherent tradeoff of reconstructing a "long screenshot" from discrete frames instead of a real OS-level API. Documented in the button's tooltip.

### v1.23.1 — one viewer counted as two (real peerId + fallback sessionId double-counted)
Follow-up to v1.23.0, from a real repro: a single viewer connecting showed "2 viewers" immediately, and closing that one tab left "1 viewer" behind instead of 0. Root cause: `makeRemoteActions()`'s dual-transport design (documented above it) means the SAME physical viewer shows up under two different `ctx.peerId` values depending on which transport delivers a given message — the real trystero peerId when P2P carries it, the fallback channel's per-tab `sessionId` when the WS relay carries it. `hello` and `viewerHeartbeat` carry no `requestId`, so they're not covered by `deliver()`'s existing dedup — every heartbeat cycle genuinely delivered twice, once per transport, each call setting a *different* key in `remoteSession.viewers`. Concretely: `hello` typically wins its first race over the fallback channel (sent immediately, before P2P has finished connecting) → one entry keyed by `sessionId`; once P2P finishes connecting, `room.onPeerJoin` fires with the real peerId → a second, separate entry. Both then get refreshed forever by every subsequent heartbeat (sent over both transports, unconditionally). On disconnect, `room.onPeerLeave` only ever gives the real peerId, so only that entry was removed immediately — the `sessionId`-keyed entry lingered until the (separate) stale-prune sweep caught it.

Fixed by having the viewer embed its own `sessionId` (already generated per tab in `makeRemoteActions`, previously only used internally) in the `hello` and `viewerHeartbeat` payloads. Host learns the `realPeerId → sessionId` mapping in a new `remoteSession.peerAliases` Map the first time either arrives via any transport, and a new `registerViewerPresence(ctxPeerId, data)` helper (used by both `handleViewerHello` and the `viewerHeartbeat` handler) collapses to a single `remoteSession.viewers` entry keyed by the canonical `sessionId`, deleting any stale raw-peerId entry in the process. `room.onPeerJoin` (a raw trystero event with no payload to carry a sessionId) still creates a temporary peerId-keyed entry the instant P2P connects, but it self-merges into the canonical entry the moment the next hello/heartbeat arrives (usually within a couple seconds, since hello retries are already in flight — see `joinAsViewer()`). `handlePeerLeaveHost()` now also looks up and deletes the aliased key when a real P2P disconnect fires, so the entry doesn't have to wait out the full `VIEWER_STALE_MS` window to disappear.

Deliberately untouched: `controlBySerial`/`apkTransfers`/`controlRequestQueue`, which are keyed by whatever `ctx.peerId` happened to win a given `controlRequest`'s (requestId-deduped) delivery — a different, narrower identity question than viewer *counting*, not evidenced as broken by this report, and riskier to touch in an already-live, well-tested feature without a specific repro pointing at it.

### v1.23.0 — viewer count never decreased after a tab close; added a persistent host banner
User report: closing a viewer's browser tab left the count in the Share modal unchanged — the count "persists" even though nobody's actually connected anymore. Root cause, previously called out in section 12 as a "known gap, low priority": `remoteSession.viewers` was only ever pruned by `room.onPeerLeave`, trystero's real-WebRTC disconnect event. That event never fires for a fallback-only viewer (WebRTC blocked on their network, e.g. Zscaler-proxied corporate networks — the exact case this app's WS-relay fallback exists for), since there's no real P2P connection to lose in the first place. A viewer who only ever used the fallback channel and then closes their tab leaves no signal behind at all under the old design.

Fixed with a heartbeat/prune pattern: `remoteSession.viewers` changed from a `Set<peerId>` to a `Map<peerId, lastSeenAt>`; every viewer now sends a lightweight `viewerHeartbeat` action every `VIEWER_HEARTBEAT_MS` (8s) over both transports; the host runs a sweep every few seconds (`remoteSession.viewerPruneInterval`) that treats any peer whose `lastSeenAt` is older than `VIEWER_STALE_MS` (25s) as gone and runs it through the *existing* `handlePeerLeaveHost(peerId)` cleanup — deliberately reusing that function rather than duplicating its control-session/APK-transfer/request-queue cleanup logic in a second place. `lastSeenAt` is also refreshed on room-join and on the existing `hello` handshake, so a real P2P peer that's merely quiet (no heartbeat needed yet) isn't pruned prematurely. Both the viewer's heartbeat interval and the host's prune interval are cleared on session teardown (`leaveRemoteSession()`, `showHostDisconnectedBanner()`, `stopShareSession()`) so nothing keeps firing after a session ends.

Also added a persistent host-side banner (`#host-share-banner` in `dist/index.html`, shown/hidden via `showHostShareBanner()`/`hideHostShareBanner()`, reusing the `.viewer-banner` CSS class since host and viewer roles are mutually exclusive per page load) showing the live viewer count outside the Share modal — previously the count was only visible while that modal was open, easy to lose track of once you'd copied the link and moved on. `updateShareModalViewerCount()` now updates both the modal's count and the banner's in one place.

Answered separately (no code change): Remote Control does **not** add to the viewer count. `remoteSession.viewers` tracks room presence only; `remoteSession.control`/`controlBySerial` (per-device control grants) is a fully separate piece of state. A single viewer tab is counted once regardless of how many devices it holds control of.

### v1.22.1 — APK install regressed to "Transfer incomplete: received 0/N chunks"
Real report: an install that worked before (v1.21.0) started reliably failing with "received 0/8 chunks" — the transfer object existed (so `apkTransferStart` had been processed) but `apkTransferEnd` ran while zero chunks had been applied yet, even though the viewer sends all chunks before End. Root cause: `apkTransferChunk` and `apkTransferEnd` are different trystero *actions*, each its own underlying data-channel stream — different streams over the same connection have **no cross-stream delivery-order guarantee**. Sending End last doesn't mean it arrives last; it's entirely possible (and, per this report, was actually happening) for End to be processed before some or all chunks land.

Fixed by making `handleApkTransferEnd()` tolerant of this instead of failing on the spot: if not all chunks have arrived yet, it polls every 200ms for up to 10s waiting for stragglers (`handleApkTransferChunk()` keeps updating the same transfer object regardless of when this wait loop is running) before giving up. Also added a `transfer.ending` guard — `apkTransferEnd` carries no `requestId`, so the generic dual-transport dedup in `deliver()` doesn't cover it, meaning a P2P+fallback duplicate delivery of the same End message could otherwise run this whole function twice concurrently and double-run `pm install`. The symmetric risk (a chunk arriving before `apkTransferStart` has been processed, currently silently dropped since `handleApkTransferChunk()` finds no transfer object yet) is **not** fixed here — not evidenced by this specific report (which showed Start had already succeeded), and buffering orphan chunks would add real complexity for an unconfirmed failure mode; worth revisiting if a future report shows partial-but-nonzero chunk loss instead of the "0 received" pattern this fix targets.

### v1.22.0 — orientation "unknown" fix, Portrait/Landscape/Screenshot, side-by-side layout
Follow-up to v1.21.0's rotation/APK-install additions, four items:

1. **Orientation always showed "unknown."** Root cause: `queryOrientation()` parsed `wm user-rotation`'s free-form printed text ("Rotation lock: enabled/disabled" + "Rotation: N") — that regex apparently never matched real device output, meaning the bare no-argument query behavior of the `wm` CLI tool isn't consistent/parseable enough across Android versions to rely on. Switched the READ side to `settings get system accelerometer_rotation` / `settings get system user_rotation` — the Settings Provider is a far more universal, stable primitive (exactly what the Settings app itself reads) than scraping a CLI tool's status text. The SET side still uses `wm user-rotation lock N`/`free` as originally requested ("by wm command") — reading and writing orientation are separate concerns here, and only the read side was ever broken. Both sides now log their raw output/response via `debugLogPush()` so a future "still shows unknown" report has real data instead of another guess.
2. **Explicit Portrait/Landscape buttons.** The existing Rotate Left/Right buttons only move *relative* to whatever the current rotation is; added a new absolute `rotateTo` `inputEvent` type (`{rotation: 0}` = portrait, `{rotation: 1}` = landscape) alongside a `setOrientation(adb, rotation)` host helper, so a viewer can force a specific orientation in one click instead of guessing how many times to hit rotate.
3. **Screenshot button.** New `screenshotRequest`/`screenshotResult` actions — deliberately separate from the continuous `screenFrame` stream (which is scaled down to ~360px for speed): `handleScreenshotRequest()` calls the existing `adbScreencap()` at *full resolution*, no scaling/recompression, and sends the raw PNG back base64-encoded (reusing `uint8ToBase64()`). The viewer triggers a browser download via a synthetic `<a download>` click — same controller-authorization check as every other control action.
4. **Layout**: the screen preview and all control rows (hardware buttons, orientation, text input, APK picker) were stacked vertically, wasting the empty space beside the (deliberately small, ~360px) mirrored screen. Wrapped them in a `.control-body` flex row (`control-screen-wrap` capped at 55% width, `.control-side-panel` taking the rest, wraps to one column on narrow viewports) — `renderControlTab()` now toggles the single `#control-side-panel` instead of four separate rows. Also fixed the APK file picker being easy to miss (a native `<input type=file>` renders almost invisibly in a dark theme): hidden via `.visually-hidden-file` and replaced with a clearly-styled `<label for="control-apk-input">` button plus a visible "chosen filename" text line — a standard accessible pattern (the label click still opens the native file picker).

### v1.21.0 — Remote Control: more hardware buttons, screen rotation, APK install
Two additions to the Remote Control tab, both only usable once a viewer has been granted control of a device (see section 12) — neither gets its own separate approval step; holding control of the device is treated as sufficient authorization for both, consistent with how tap/swipe/keyevent/text input already work.

- **More hardware buttons + screen rotation**: added Volume Up (keyevent 24), Volume Down (25), and Notifications/expand shade (83) next to the existing Back/Home/Recent/Power row. Rotation is a new pair of `inputEvent` types (`rotate` with `{direction: 'left'|'right'}`, `setAutoRotate`) instead of a plain keyevent, since it needs a read-modify-write round trip: `queryOrientation(adb)` runs `wm user-rotation` and parses `Rotation lock: enabled/disabled` + `Rotation: N` (N is a 0-3 index matching `Surface.ROTATION_*`, not literal degrees); `handleInputEvent()`'s new branch computes `(current ± 1) mod 4` for rotate or issues `wm user-rotation free` for auto-rotate, then re-queries and pushes the result back via a new targeted `orientationStatus` action. The host also proactively sends one `orientationStatus` right when control is granted (`grantControlRequest()`), so the badge shows real state immediately rather than waiting for the first rotate click. Viewer state: `controlBySerial[serial].orientation`, rendered by `renderControlTab()`/`setOrientationBadge()`; devices that don't support `wm user-rotation` at all show "unknown" rather than a misleading default.
- **APK install**: a file input (`.apk` only, 200MB cap) in the Remote Control tab. The viewer reads the file into memory, base64-encodes it in 200KB chunks (reusing the existing `uint8ToBase64()` helper, originally written for screen frames), and sends them via three new actions — `apkTransferStart` (metadata: filename/size/totalChunks), `apkTransferChunk` × N (`{index, data}}`, assignment into a pre-sized array is naturally idempotent so a dual-transport duplicate delivery is harmless with no extra dedup bookkeeping needed), `apkTransferEnd` (triggers assembly + install). The host (`handleApkTransferStart/Chunk/End`) verifies the sender is the CURRENT controller for that serial+grantId on every single message (not just at start) — the same enforcement `handleInputEvent()` already does — then on `End`, concatenates the chunks, pushes to `/data/local/tmp/<sanitized-filename>` via `adb.sync().write()` (the library's real sync-protocol push — confirmed via reading `@yume-chan/adb`'s `AdbSync.write()`/`adbSyncPush()` source; this is genuinely the right tool here, unlike `readDeviceFile()`'s deliberate shell-`cat`-instead-of-sync choice for small text reads, since a multi-MB binary is exactly what the sync protocol exists for), then runs `pm install -r` (120s timeout) and reports `apkInstallResult` back to the viewer, cleaning up the temp file via `adb.rm()` either way. In-memory only (`remoteSession.apkTransfers`, host-only, cleaned up on peer-leave/device-removal alongside the existing `controlBySerial`/`controlRequestQueue` cleanup) — never touches disk beyond the device's own `/data/local/tmp`.

### v1.18.0 — actual root cause of "Waiting for host data…", found via v1.17.2's logging
The v1.17.2 diagnostic logging paid off immediately: a real viewer debug log showed the *non-active* (v1.17.0-prefetched) device's Properties/Features/Packages arriving and rendering perfectly — `handleTabDataPush: received serial=25119524202582 ...` — while `applyMirroredTabsForSerial(260195242D0335)` (`260195242D0335` being `mirror.activeSerial`, i.e. the device the host actually had selected and was looking at) logged `cached tabs=[]` on every single call. The bug was the **exact inverse** of what v1.17.0 assumed.

Root cause: `startShareSession()`'s v1.17.0 prefetch loop explicitly *skipped* `activeSerial`, reasoning it was "already fresh from being selected." That's only true if the device was selected *after* a share session already existed. In the normal workflow — connect a device (which auto-selects and fetches it immediately) *then* click Share — `pushTabHtml()` (called from `selectDevice()`'s fetch chain) runs while `remoteSession` is still `null`, and its very first line (`if (!remoteSession || ...) return;`) makes it a silent no-op. Nothing ever re-triggers those fetches afterward, so `hostTabHtmlCache[activeSerial]` stayed permanently empty — the currently-viewed device's data was sitting fully rendered in the host's own DOM the whole time, just never captured for viewers.

Fixed by having `startShareSession()` explicitly (re-)broadcast `activeSerial`'s already-rendered tab HTML the moment sharing starts — a loop over `mirroredTabElementIds()` calling `pushTabHtml(tab, elementId)` (now that `remoteSession` exists, this actually sends) — pulling straight from the live DOM, no new adb round-trips needed since the host is already looking at exactly this data. This also covers Attestation/RKP for the active device for free, since `selectDevice()` already fetches all five tabs automatically (confirmed by re-reading its fetch chain) — only the non-active-device prefetch (`prefetchTabsForViewers()`) deliberately excludes those two as too slow to run unconditionally in the background.

This is a good example of why the v1.17.2 logging-first approach was the right call after two failed guesses: the actual bug was completely different in *shape* from every prior theory (device-never-clicked, targeted-send-identity-mismatch) — it was an ordering dependency between "device gets auto-selected" and "sharing starts," invisible without a full request-to-render trace.

### v1.17.1 — v1.16.1's connect serialization could deadlock all future connections
Real Windows debug log: a second device's connect sequence logged `usbDevice.connect() resolved after 0ms` and then simply went silent forever — no `AdbDaemonTransport.authenticate()` line, no SUCCESS, no FAILED, nothing — while the app otherwise carried on (a share session started fine 13s later). Root cause: v1.16.1's fix for the hub-reset-ripple issue serialized `connectDeviceExclusive()` calls behind a promise-chain mutex (`connectQueue`), covering the ENTIRE call including `AdbDaemonTransport.authenticate()` — which can legitimately take an unbounded amount of time (e.g. waiting on an on-device RSA key confirmation prompt the user hasn't tapped yet). A mutex has no timeout concept: if one call never settles (never resolves OR rejects), every subsequent `connectDevice()` call queues behind it **forever**, silently — no error, no timeout, just permanently jammed. This is strictly worse than the bug it was meant to fix.

Replaced with a bounded stagger instead of an unbounded queue: `connectDevice()` now just enforces a minimum ~1.2s gap between when consecutive `connectDeviceExclusive()` calls **begin** (`MIN_CONNECT_START_GAP_MS`/`lastConnectStartAt`), comfortably longer than the observed reset/open/close duration (well under 1s in every captured log), but it never waits on a previous call's actual *completion*. Worst case this adds a flat ~1.2s delay before a new connect attempt starts; it can never block indefinitely on another device's hang, no matter how long that hang lasts. Still meaningfully reduces the odds of two devices' risky open/reset/close sequences landing at the literal same instant, which was the actual goal — just without the mutex's catastrophic failure mode.

Separately noticed in the same log (not yet investigated/fixed): `startShareSession()` triggered **20** `RTCPeerConnection` objects being created simultaneously the instant the room was joined, all immediately failing ICE gathering against every configured STUN/TURN server. The fallback channel still connected fine right after, so this didn't block the session, but it's real wasted work — possibly stale/zombie peer state accumulated on the shared self-hosted relay from this project's own extensive iterative testing (many start/stop cycles, not always cleanly closed), or a genuine characteristic of how trystero's relay-based room joining discovers peers on a shared topic before the password-based handshake filters out non-matching ones. Worth a closer look if it recurs or if session-start latency becomes noticeable.

### v1.17.0 — viewer "Waiting for host data…" for devices the host never personally clicked
Follow-up report after v1.16.0's broadcast-instead-of-targeted fix: some devices *still* showed "Waiting for host data…" for every tab, with no discernible pattern from the viewer's side. Root cause, found by tracing `connectDeviceExclusive()`'s success path: only the **first** device connected each session gets auto-selected (`if (connectedDevices.size === 1) selectDevice(adbSerial)`) — `selectDevice()` is what triggers `fetchProperties()`/`fetchFeatures()`/`fetchPackages()`/`fetchAttestation()`/`fetchRKP()`, so any *second or later* connected device has **nothing fetched for it at all, anywhere**, unless the host personally clicks that device's card in their own sidebar. A viewer selecting one of those never-clicked devices was seeing entirely correct behavior given the data genuinely didn't exist yet — just with no way to tell that from the viewer side, hence "I cannot find the rule."

Fixed by proactively fetching Properties/Features/Packages (deliberately not Attestation/RKP — see below) for every OTHER connected device once a remote session is active, without ever touching the host's own visible tabs:
- `propsToHtml(props, query)` / `featuresToHtml(features, query)` / `packagesToHtml(packages, fallback, method, query)` are pure HTML-string-building functions extracted out of `renderProperties()`/`renderFeatures()`/`renderPackages()` (mechanical extraction — the existing render functions are now thin wrappers that read the search-box query from the DOM and delegate; no behavior change to the local host UI). Similarly `parseGetprop(text)`/`parsePmListFeatures(text)` were pulled out of `fetchProperties()`/`fetchFeatures()`'s inline parsing (`parseDumpsysPackage`/`parsePmListPackagesFallback` already existed as standalone functions).
- `prefetchTabsForViewers(serial)` (new) calls these directly against an arbitrary serial's `adb` object and writes straight into `hostTabHtmlCache` + broadcasts via `cacheAndBroadcastTabHtml()` (a `pushTabHtml()` variant that takes an explicit serial instead of always using `activeSerial`) — critically, it never touches `activeSerial`, `dataCache`, or any live DOM element, so it can never flicker/corrupt whatever the host is actually looking at, even though `dataCache.props`/`.features`/`.packages` are single global (not per-serial) caches that the LOCAL fetch functions do write into.
- Called from two places: `connectDeviceExclusive()`'s success path (for a device connected *while already sharing* — `else if (remoteSession?.role === 'host') prefetchTabsForViewers(adbSerial)`, right next to the existing first-device auto-select branch) and `startShareSession()` (loops every already-connected device except `activeSerial` when a share session starts). Gated on an active host session specifically — no extra background shell traffic for purely local (non-shared) usage, which is still this app's primary use case.
- Attestation/RKP are deliberately excluded: both are slower, real hardware/keystore probes (can take several seconds and, for attestation, involve actual key generation) — not worth running unconditionally for a device that may never be looked at remotely. Those two tabs keep the pre-existing behavior (populate the first time *any* click, host or viewer-prompted, visits that tab locally).

### v1.16.1 — Linux: a second device's connection attempt could bump an already-connected one
Real Linux multi-device debug logs (2026-08-11) showed a device that had *already connected successfully* getting torn down the moment a **second** device's connection attempt started — `USB disconnect event` (no serial, as usual on Linux) landed on the already-connected device via the vid+pid fallback match (unambiguous, since it was the only one of that vid+pid actually in `connectedDevices` at the time), immediately followed ~1-2s later by a `USB connect event` for the same vid+pid. That timing strongly points to the SECOND device's `connectDevice()` — specifically its pre-emptive `usbDevice.raw.reset()` call — rippling a spurious disconnect across the first device on a shared USB hub/controller, not a real unplug. Two fixes, complementary:

1. **Self-healing (`pendingAutoReconnect`)**: `handleUsbDisconnect()`'s matched-teardown path (i.e., anything that reaches teardown at all — an explicit user-initiated disconnect is already suppressed earlier and never reaches this point) now marks that serial for auto-reconnect, with a 20s expiry. `scanAvailableDevices()` checks this set every time a device reappears as available and, if marked, immediately calls `connectAvailable()` for it instead of waiting for the user to notice and click Connect. Costs nothing for a genuine unplug (the attempt just exhausts its retries and it sits in "available" same as before); fully recovers the common phantom-disconnect case with no user action.
2. **Serialization (`connectQueue`)**: the actual body of `connectDevice()` was renamed to `connectDeviceExclusive()`; the public `connectDevice()` name is now a thin wrapper that runs every call through a simple promise-chain mutex, so no two devices' `open()`/`reset()`/`close()` sequences can ever execute at the literal same instant — a real (if partial) mitigation of the underlying hub-contention cause, not just a reaction to its symptom. Deliberately scoped to only the individual `connectDeviceExclusive()` attempt, not the whole `connectWithRetries()` backoff cycle — otherwise a second device could get stuck waiting up to ~45s (the full retry budget) behind an unrelated struggling device instead of just avoiding overlap with its brief connect attempts specifically.

This is a real hardware/driver-level quirk (shared-hub reset propagation) working around it from the browser side is inherently best-effort — not fully verifiable without the reporter's actual multi-device Linux hardware, so this needs their confirmation it actually resolves both scenarios in their logs (one-device-at-a-time and two-at-a-time).

### v1.16.0 — per-device remote control, real fps fix, viewer tab-data regression, viewer version display
Four more reports right after v1.15.0 shipped:

1. **Remote Control wasn't per-device.** v1.15.0's control persistence fix (pinning control to `remoteSession.control.serial` independent of the sidebar) was still built on a SINGLE global control slot — meaning there could only ever be one control session at all, for one device, across the whole host, and the Remote Control tab always showed that one session regardless of which device was actually selected. Restructured to be genuinely per-device: host state is now `remoteSession.controlBySerial: Map<serial, {peerId, grantId, seq, lastInputSeq}>` and `remoteSession.controlRequestQueue: [{peerId, serial, requestId}, ...]` (a queue, since multiple simultaneous requests for different devices are now a real possibility — reviewed one at a time via a single reused Grant/Deny modal that auto-advances). Viewer state is `remoteSession.controlBySerial: {serial: {active, grantId, lastAppliedSeq, inputSeq, lastFrameW, lastFrameH, lastJpeg}}`. `setMirrorActiveSerial()` now calls `renderControlTab()` on every device switch, which redraws the Remote Control tab from whatever's true for the newly-selected device's own entry — a session for a device you switch away from keeps running untouched in the background (frames keep arriving and get cached via `lastJpeg`) and reappears instantly on switching back, satisfying both "each device has its own instance" and the earlier "don't drop control on switch" fix simultaneously. The active-control banner (`showControlActiveBanner()`) is now a full re-render showing one row per currently-controlled device (plural now possible), each with its own Stop button.
2. **fps still too low after the v1.15.0 delay fix — real cause found.** Making `screenFrame`/`inputEvent` fully dual-transport (v1.14.1, to fix a P2P-less viewer's permanently-broken screen) meant `encryptForFallback()` ran on *every single frame* even when P2P was working perfectly fine: it JSON.stringifies the whole envelope, runs AES-GCM, then JSON.stringifies the ciphertext AGAIN as a plain array of numbers — all synchronous main-thread work that scales with payload size, directly competing with the fps it was supposed to help. Fixed by making the wrapper adaptive instead of all-or-nothing: `wrap()`'s `send()` now checks `room.getPeers()[opts.target]` and skips the fallback send for these two high-frequency actions specifically when there's already a live P2P connection to that exact target, falling back only when there isn't (unknown target, or a genuinely fallback-only/Zscaler-style viewer — the case this path exists for). Also trimmed frame size a bit further (400px/0.5 → 360px/0.45) and fixed a latent bug found while touching this code: `real.send()` is `async` and the surrounding `try/catch` around a bare (unawaited) call never actually catches a later rejection — wrapped in `Promise.resolve(...).catch(() => {})` so a failed send can't surface as an unhandled-rejection console error.
3. **Viewer tab-data regression: every tab, every device, "Waiting for host data…" (this had briefly worked before v1.15.0's own attempted fix for a narrower version of the same gap).** Root cause: `handleViewerHello()`'s catch-up dump used `tabDataPush.send(data, {target: peerId})`, TARGETED at whichever `ctx.peerId` the triggering `hello` happened to arrive with. Since dual-transport delivery means `ctx.peerId` is a DIFFERENT string depending on which transport delivered a given message (real trystero peerId vs. the fallback's per-tab session UUID — see `makeRemoteActions()`), a targeted send only actually reaches the recipient over the ONE transport whose own identity matches the `target` value; the other transport's own target check (`if (target && target !== sessionId) return`) silently drops it. If the transport that happened to deliver that specific `hello` wasn't the one the viewer was actually reachable on for the *reply*, the whole catch-up dump was silently lost — explaining "every tab, every device" (the live/broadcast pushes from `pushTabHtml()` during an active session still worked fine, since those are untargeted). Fixed by making the catch-up dump broadcast (no `target`) instead of targeted — costs a redundant re-send to every other already-connected viewer (harmless, and only happens when someone new joins), but sidesteps the identity-matching problem entirely. This same targeted-send-to-a-cross-transport-identity risk is worth remembering for any *future* one-off targeted send that doesn't have a request/response's natural symmetry (which is what protects `cmdResponse`/`pathCompleteResult`/`controlResponse`/etc. — they always reply using the exact same `ctx.peerId` a given request arrived with, so request and reply are always transport-consistent even though the *value* varies message to message).
4. **Viewer page didn't show a version number.** `#header-version` (in the shared `.header`, not hidden in viewer mode) already got set on every page load regardless of role, so this may have been more about visibility/prominence than a strict absence — added a second, explicit `#viewer-version` span directly in `#viewer-banner` (viewer-exclusive UI) either way, set from the same `init()` code path that sets `#header-version`.

### v1.10.2 — CRITICAL: v1.10.0/.1 broke real P2P message handling entirely (worse than v1.9.x)
Even after v1.10.1 fixed the crash, no viewer could connect at all — worse than before the fallback-channel work, on every network including ones that never needed a fallback. Root cause: trystero's real action objects (`room.makeAction(name)`) expose `onMessage` as an **assignable property with a setter** (`actions.mjs`: `get onMessage() {...}`, `set onMessage(handler) { onMessage = handler; ... }`), not a callable method — every single registration in this codebase, on both host and viewer, does `actions.foo.onMessage = handler`. `makeRemoteActions()`'s `wrap()` function returned a plain object literal with `onMessage: (handler) => { real.onMessage(handler); ... }` — a function-*valued* property, not a getter/setter. Assigning to a plain property (`actions.foo.onMessage = handler`) just **overwrites** it with the raw handler — it does not *call* the function that used to be there. So `real.onMessage(handler)` inside my wrapper never ran, meaning `real.onMessage = handler` (the actual trystero registration) never happened, meaning trystero never told any registered listener about incoming P2P messages — for any action, on any connection, fallback or not.

Fixed by making the wrapped `onMessage` a genuine `get`/`set` pair, mirroring trystero's own shape exactly: the setter now does `real.onMessage = handler` (correct trystero registration) *and* `dispatchers[name] = handler` (fallback dispatch). Verified with a standalone Node script simulating both a real-P2P-delivered message and a fallback-delivered message reaching the same registered handler correctly before shipping.

Lesson: when wrapping/proxying an existing library's object API, check whether each member is a method or an accessor property (`get`/`set`) — object-literal shorthand (`onMessage: (h) => {...}`) silently produces the wrong shape for the latter with no error at definition time, only a silent no-op the first time a caller assigns to it.

### v1.10.1 — CRITICAL: v1.10.0 broke every button on the viewer page for everyone
v1.10.0 introduced `const REMOTE_ACTION_NAMES = [...]` at module scope, positioned (in source order) *after* `(function init() {...})()` — but `init()` runs immediately at module load and, on the viewer page (`#room=...&key=...` present), synchronously calls `initRemoteViewerIfLinked()` → `joinAsViewer()` → `makeRemoteActions()`, which referenced `REMOTE_ACTION_NAMES` before the module's top-level execution had ever reached that `const`'s own declaration line. That's a classic temporal-dead-zone `ReferenceError` — thrown synchronously, uncaught, from inside `init()`'s IIFE.

The consequence was total: an uncaught exception during a top-level IIFE call aborts the *entire remaining module evaluation* — every `window.fn = fn` assignment anywhere later in the file (which is how literally every `onclick="..."` handler in `dist/index.html` gets wired up, per this app's own single-file/no-framework convention) simply never ran. Confirmed with a minimal repro (see commit) that reproduces exactly this: nothing after the throwing call executes, not even unrelated code. This is why the report was "all buttons are not responsive," on *every* viewer — not just the Zscaler one — deterministically, independent of network conditions. The host page was unaffected (`makeRemoteActions()` there is only called later, from `startShareSession()` on a manual click, by which point the module had long finished loading and the `const` was long since initialized).

Fixed by removing the module-level `const` entirely — the action-name list is now a plain array literal inline inside `makeRemoteActions()`'s own body, a normal local variable with no cross-module ordering dependency. General lesson for this codebase, given `init()` runs sync code immediately at the top of the file: any new top-level `const`/`let` (not a `function` declaration — those are fully hoisted and immune to this) must either be declared *before* line ~117, or, more simply, just not be top-level at all unless it truly needs to be shared across functions.

### v1.10.0 — relay-based fallback data path (works around Zscaler/corporate-proxy networks that break WebRTC entirely)
`makeDiagnosticRTCPeerConnection()` (v1.9.3) finally gave a real answer: for a viewer on a Zscaler-proxied corporate network, every single STUN/TURN server — Google's, Cloudflare's, Open Relay's — failed identically with `errorCode=701`, split cleanly into two failure modes: UDP-based entries failed at DNS lookup ("STUN/TURN host lookup received error"), TCP-based ones got further but failed to establish a connection. That specific split — not a blanket DNS outage, but a UDP-specific block plus a TCP-based TURN attempt that gets further before failing — is the signature of a corporate SSL-inspecting proxy (confirmed: the user's machine runs Zscaler, mandatory, cannot be disabled) breaking WebRTC's ICE/TURN mechanics outright, regardless of which TURN provider is configured. No TURN provider swap (paid or free) can fix this — it's not a provider reliability problem.

What *has* worked, in every single log captured across this entire investigation, without exception: the plain WSS connection to our own self-hosted signaling relay (`web-adb-inspector-relay.onrender.com`). It's indistinguishable from ordinary HTTPS traffic to Zscaler, so it always gets through.

Realized the relay doesn't have to be signaling-only: `@trystero-p2p/ws-relay`'s server (`relay-server/node_modules/@trystero-p2p/ws-relay/dist/server.mjs`) is a **generic topic-based pub/sub** — arbitrary `subscribe`/`unsubscribe`/`publish` to any topic string — not a WebRTC-specific protocol. A second client speaking that exact same protocol, on a room-scoped topic (`webadb-fallback-<roomId>`), can carry the actual session traffic (device state, shell commands/output) as a parallel path, with **zero changes to the relay server itself**.

Added (`src/index.js`, replacing the old `makeRemoteActions`):
- `createFallbackChannel(roomId, password, sessionId, label)` — a raw `WebSocket` client for the relay's pub/sub protocol, independent of trystero/WebRTC entirely. Auto-reconnects, queues sends while disconnected.
- `deriveFallbackKey()`/`encryptForFallback()`/`decryptFromFallback()` — AES-GCM, keyed by SHA-256 of the room password (the same shared secret already in the share link). Needed because, unlike the P2P path (encrypted end-to-end by WebRTC itself), this now transits our own Render-hosted server and shouldn't be readable there.
- `makeRemoteActions(room, roomId, password, label)` — now wraps every action so `send()` goes out over **both** the real P2P data channel (best-effort, silently a no-op if trystero doesn't recognize the target — same as its own existing behavior) and the fallback channel, and `onMessage()` is registered on both. Every existing caller (`handleRemoteCmdRequest`, `sendRemoteCommand`, `executeRemoteShell`, etc.) needed **zero changes** — they only ever see `{send, onMessage}` and a `ctx.peerId`, which is now either a real trystero peerId or (fallback-only) the sender's random session UUID; both are stable opaque strings for the session's lifetime, which is all the existing `ctx.peerId === remoteSession.hostPeerId`-style checks actually need.
- Incoming messages carrying a `requestId` (cmdRequest/cmdResponse/pathComplete/pathCompleteResult) are deduped by `action:requestId` in case both transports deliver the same logical message — matters most for `cmdRequest`, where a duplicate would otherwise re-execute a shell command.
- Viewer-side gap: `hello.send()` used to only fire from `room.onPeerJoin`, a P2P-only event that never fires if P2P never connects at all. Added a proactive fallback-only `hello` broadcast (retried a few times over ~6s, since pub/sub doesn't buffer for a topic-subscriber that joins a moment late) right after `joinAsViewer()` sets up the channel, independent of any P2P event.
- `stopShareSession()`/`leaveRemoteSession()` now also close the fallback WebSocket.

Fixed in v1.23.0 (see section 7): `remoteSession.viewers` no longer relies solely on `room.onPeerLeave` (a P2P-only event) to prune stale entries — a heartbeat/prune sweep now catches fallback-only viewers too.

### v1.9.0 — definitive RKP provisioning check (cmd remote_provisioning certify)
The existing RKP tab (`fetchRKP()`) checked KeyMint/HAL/GMS/boot-security signals but never actually confirmed *provisioning* — it inferred RKP health from `cmd keystore`, HAL service registration, and a TLS reachability probe to Google, none of which prove that provisioning certificate material exists on the device. Per a reference procedure the user provided ("Android RKP Provisioning Verification via ADB"): package/HAL/config presence only proves RKP is *supported and configured*; the only reliable ADB-level proof is `cmd remote_provisioning certify <component>` returning a real PEM certificate chain.

Added `checkRkpProvisioning(adb)` (`src/index.js`, next to `checkAttestationCapability`) implementing that procedure's decision hierarchy:
1. RKP package presence + enabled state (`pm list packages | grep rkpd`, `dumpsys package com.google.android.rkpd`).
2. Enumerate components (`cmd remote_provisioning list` — typically `default`/`strongbox`).
3. Config (`remote_provisioning.hostname`, `remote_provisioning.tee.rkp_only`).
4. **The definitive step**: for every enumerated component, run `cmd remote_provisioning certify <name>` and check the response actually contains `-----BEGIN CERTIFICATE-----`. Only this is reported as `PROVISIONED`; anything else is `NOT CONFIRMED` with whatever the device returned as a note.

### v1.8.1 — Tab completion now escapes names with spaces (and re-completing across them)

### v1.8.0 — Tab-key path completion, host + viewer; clarified the `ls -l` `?????????` question
Two things came out of the same user report.

**The `?????????` columns in `ls -l /sys/power`** are not a bug in this tool — `adb shell` on a non-rooted/userdebug build runs as the unprivileged `shell` user, and `ls -l` prints that placeholder for any entry it can't `stat()` (common for sysfs nodes owned by `root` with restrictive permissions). Running the exact same `ls -l /sys/power` from a real terminal's `adb shell` shows identical output — nothing our command-wrapping changes. Worth documenting here since it's likely to come up again.

**Tab completion**, actually a feature gap: added `runTabCompletion()` (`src/index.js`, shared by both shells) — on Tab, it takes whatever path-looking word sits before the caret, splits it into a directory part and a name prefix, asks for a directory listing, and either completes to the single match (adding a trailing space for files, not directories) or to the longest common prefix across multiple matches (classic shell behavior; a second Tab press to list all candidates was **not** implemented — out of scope for now).
- Host Shell tab: `completeShellPath()` calls `adbShellTimed` directly with `ls -1Ap '<dir>'` (reusing `wrapWithCwdTracking`/`extractCwdMarker` so the listing resolves against the tracked cwd) — no round-trip needed, it already has the `adb` object.

### v1.7.1 — fixed extractCwdMarker() finding the wrong marker occurrence
v1.7.0 shipped `cd` tracking that didn't actually track anything: `pwd` after `cd storage` still reported `/`, and the raw `@@ADBWEB_CWD@@<path>` marker text leaked straight into the visible console instead of being stripped. Root cause: `extractCwdMarker()` used `lastIndexOf(CWD_MARKER)` to find "the" marker, but the wrapped command emits *two* adjacent copies of it (`'<MARKER>' "$PWD" '<MARKER>'`, no separator between the path and the closing one) — `lastIndexOf` landed on the closing copy, so the visible "text" slice (everything before that index) still included the opening copy plus the path, and the "cwd" slice (everything after) was just trailing whitespace, which parsed to empty and silently fell back to `null` — so the tracked directory never advanced past its initial state. Fixed by using `indexOf` for the first marker and searching for the second occurrence starting *after* it, so the path between them is what gets extracted and both marker copies are correctly excluded from the visible text.

### v1.7.0 — persistent-feeling `cd` and a visible current-directory prompt, host + viewer
Every `adb shell <cmd>` call is a brand-new process with no memory of the last one, so `cd /sdcard` typed into either Shell tab did nothing to the *next* command — a real, longstanding usability gap the user called out directly ("extremely restricts the usage").

Faked persistence rather than opening an actual interactive/PTY session (`sp.pty()` exists in `@yume-chan/adb` but would mean a much bigger rewrite of the one-shot request/response model both shells use): every command sent to the device is wrapped as `cd '<last-known-dir>' 2>/dev/null\n<user command>\nprintf '\n%s%s%s\n' '<MARKER>' "$PWD" '<MARKER>'` (`wrapWithCwdTracking()`/`extractCwdMarker()`, `src/index.js`, next to `adbShell`/`adbShellTimed`). Because it's one shell invocation, the user's own `cd` (or `pushd`, or whatever) takes effect before the trailing `printf`, so `$PWD` always reflects wherever the command actually left the shell — that becomes the tracked directory for the *next* command. No special-casing of `cd` as a command was needed; this works for anything that changes directory.

Verified the round-trip is safe through `@yume-chan/adb`'s `splitCommand()`/`command.join(" ")` (client-side space-tokenize, then rejoin before sending as the `shell,v2,raw:` service string) — since the wrapped command only ever has single spaces between tokens and embeds real newlines *inside* tokens (newline isn't a delimiter to that tokenizer), split+rejoin round-trips it byte-for-byte, so the device's `sh -c` sees exactly the multi-statement script intended.

- Host's local Shell tab: `dataCache.cwdBySerial[serial]`, updated in `runShell()`, displayed via `updateShellCwdLabel()` (`#shell-cwd`, restored on `selectDevice()` device-switch alongside the existing `shellBySerial` restore).
- Remote shell: host tracks cwd **per (viewer peerId, serial)** in `remoteSession.viewerCwd` (a `Map`) inside `executeRemoteShell()`, so two viewers (or a viewer and the host's own local session) don't stomp each other's directory. The resolved cwd rides back on `cmdResponse.cwd`; the viewer stores it in `remoteSession.mirror.cwdBySerial[serial]` and shows it via `updateViewerCwdLabel()` (`#viewer-shell-cwd`), refreshed on every `renderMirrorDeviceList()` call so it stays correct across device switches too.
- Both echoed prompt lines now show the directory the command actually ran in (`<dir> $ <cmd>` on host, `[device] <dir> $ <cmd>` on viewer) instead of a bare `$`.
- Found and fixed, in passing: a literal NUL byte (0x00) had ended up in `src/index.js` in place of an intended space character while authoring this change (`peerId + ' ' + serial`) — `esbuild` bundled it without complaint (NUL is valid inside a JS string literal), so it would've shipped silently. Caught it because `Grep`'s content mode refuses to print through a NUL and says so explicitly; patched the single byte back to `0x20` and confirmed no other occurrences in the file. Worth remembering as a sanity check if a grep unexpectedly reports "binary file matches" in this text-only source file again.

### v1.5.8 — try USBDevice.reset() (a real bus-level reset) as a cheaper alternative to the iframe-isolation idea
Before committing to a same-origin-iframe "mini-reload" architecture (a real but complex/uncertain option — discarding any browsing context, not just the top-level page, triggers the same WebUSB cleanup per spec, so a disposable iframe per connection attempt could in principle avoid needing a full page reload), tried the cheaper option first: `USBDevice.reset()`. Unlike `open()`/`close()` (which only manage the *browser's logical claim/handle*), `reset()` performs an actual USB-protocol-level bus reset — the software equivalent of physically unplugging and replugging the device. Added it to both existing cleanup points:
- The pre-emptive cleanup before every attempt (v1.5.6): now `open()` → `reset()` → `close()` (each independently best-effort; `reset()` requires the device to already be `opened`, hence `open()` first) instead of just `close()`.
- The post-failure catch-block cleanup (v1.5.5, for when `usbDevice.connect()` succeeds but a later step fails): now `reset()` before `close()`, instead of just `close()`.

Not yet confirmed whether this resolves the issue — if it doesn't, the next step is the iframe-isolation approach, or accepting the v1.5.7 one-click Reload button as the practical answer going forward.

### v1.5.7 — accepted this can't be fixed purely in-page; added a one-click Reload
v1.5.6's pre-emptive `close()`-before-every-attempt *also* didn't recover it — confirmed the exact same "Failed to execute 'open'... device was disconnected" error persisted through a full 7-attempt retry cycle even with that in place. That result actually rules out the "still open from a previous attempt" theory entirely: an unconditional `close()` before every attempt, including the very first, should clear any such state if that were the real cause, and it didn't.

Revised (final, for now) theory: this is most likely a problem inside the browser's own per-page WebUSB bookkeeping, not in anything our device-object handling can reach. Chrome/Edge's WebUSB implementation is backed by a connection between the page and the browser's internal USB service for each device; if that gets into a bad state, `getDevices()` calls within the *same page* may keep handing back references tied to that same broken internal state no matter how many times it's re-fetched or how carefully `open()`/`close()` are sequenced from script. Only an actual page reload tears down and re-establishes that connection — which matches every observation throughout this entire investigation: hard refresh has been 100% reliable; nothing else has, including several different open/close strategies.

Given that, no further in-page JS retry/cleanup logic is expected to fix this — accepted this needs a real reload, and made that reload one click instead of manual: `showADBReleaseDialog()` is no longer a plain `alert()`; it's a proper modal (matching the existing Share/Help modal style) with a **Reload Page** button (`location.reload()`) alongside the existing troubleshooting guidance, shown whenever `isDeviceBusyError()` matches — which includes the final failure after all of `connectAvailable()`/`scanDevices()`'s retries are exhausted.

### v1.5.6 — v1.5.5 wasn't sufficient: pre-emptive close-before-open added
v1.5.5's cleanup only runs when `usbDevice.connect()` itself *succeeds* and a later step (almost always `AdbDaemonTransport.authenticate()`) fails afterward — it does nothing for `Failed to execute 'open' on 'USBDevice': The device was disconnected'`, since that error comes from the `open()` call itself rejecting, meaning `openedConnection` never becomes `true` and there's nothing for that catch-block cleanup to close. Confirmed this exact error still persisted across a full 7-attempt retry cycle (twice) even with v1.5.5 deployed — a hard refresh was still needed to recover.

Leading theory: the underlying `@yume-chan/adb-daemon-webusb` library's `connect()` sequence can partially succeed (the native `open()` call) before failing at a later *internal* step (e.g. claiming the interface) — without ever handing our code a connection object to close ourselves, since the overall `connect()` promise it returns still just rejects. That would leave the *native* device open from a previous attempt's perspective, and Chrome/Edge's WebUSB implementation apparently doesn't tolerate a second `open()` from the same page while that lingering state exists — causing the next attempt's `open()` to reject immediately with the same "disconnected"-sounding message. Only a full page reload (forcing the browser to release everything the page held) recovers, matching what's been observed throughout.

Fix: `connectDevice()` now unconditionally calls `await usbDevice.raw.close()` (ignoring any error) *before* every attempt, not just in a catch block after one already failed — clearing any lingering native-open state a previous attempt might have left, regardless of exactly which internal step that attempt failed at. This is a more defensive, "always start from a known-closed state" strategy layered on top of (not replacing) v1.5.5's after-the-fact cleanup.

If this *still* doesn't fully resolve it, the next step would be to test with `AdbDaemonWebUsbConnection`-level instrumentation (patching/logging inside `@yume-chan/adb-daemon-webusb` itself, or filing an upstream issue) to find exactly which internal step is leaking — this is about as much as can be fixed from the outside of that library without forking it.

### v1.5.5 — FIXED (likely the real root cause all along): leaked USB claim on failed connect never released
The actual smoking gun (2026-08-06): re-toggling "USB debugging" on the device (which re-triggers Android's authorization prompt, confirmed accepted) and re-pairing still failed all 7 retries (~44.5s) — but a hard refresh right after immediately succeeded. If the underlying block were external/timing-based (e.g. the CrowdStrike scan-window theory), more retrying *within the same page* should work just as well as after a refresh — external systems don't care whether the page reloaded. But a hard refresh does exactly one relevant thing: it force-releases every WebUSB claim held by that page. That pointed back at our own code.

Found it: `connectDevice()`'s catch block never closed the `connection` object (or the device) when `AdbDaemonTransport.authenticate()` failed *after* `usbDevice.connect()` had already succeeded (i.e. already claimed the USB interface). Every failed attempt — and there have been many, across this whole investigation — leaked a claimed interface that the browser kept associated with the page for its entire remaining lifetime. Retrying with a freshly-refetched device object doesn't help, because the leak isn't about *which device object* you hold, it's an OS-level claim the page never released. Only a full reload (which the browser cleans up on unload) clears it — which is the entire explanation for "hard refresh reliably fixes it" observed throughout this investigation, and likely means the CrowdStrike/endpoint-security theory (while plausibly still a contributing factor for the *first* failure in a sequence) was mostly a red herring for why retries kept failing afterward — each retry was doomed by the leak from the *previous* attempt, not by an external block.

Fix: `connectDevice()` now tracks whether `usbDevice.connect()` succeeded (`openedConnection`), and if a later step throws, calls `usbDevice.raw.close()` (the standard native `USBDevice.close()`, not anything yume-chan-specific — closing the device is what actually releases the OS-level claim) before returning `false`, wrapped in its own try/catch so a failure to close doesn't mask the original error.

### v1.5.4 — retry logic reaches the initial "+Connect Device" picker path too; widened further; confirmed not device-specific
Follow-up (2026-08-06) to v1.5.3. Two important refinements:

1. **It's not FR55-specific.** Forgetting and freshly re-pairing TC201 (previously 100% reliable) reproduced the exact same failure. The real trigger is "freshly `forgetDevice()`'d + re-paired via the picker" for *any* device, not a policy block on one specific VID — an already-established connection reconnects fine regardless of which device. This is a stronger fit for the CrowdStrike-scan-window theory (a fresh permission grant looks like a "newly attached" event worth (re-)scanning) than a per-VID deny policy (which would fail identically regardless of how long you wait).
2. **`scanDevices()` (the "+Connect Device" native-picker path) had zero retry logic at all** — only `connectAvailable()` (the "Ready to Connect" reconnect path) retried. So a fresh pairing's first (and only) attempt failing required the user to notice it landed in "Ready to Connect" and manually click Connect there to reach the retry-capable path — observed directly: "it doesn't connect automatically hence I have to click connect button."
3. **"Hard refresh fixes it" is misleading** — a refresh can't change anything at the USB/OS level (confirmed: VID is fixed hardware descriptor data, doesn't change). The refresh-plus-manual-retry cycle just takes real wall-clock time (10-30+ seconds), which is probably long enough for the transient block to clear on its own — i.e., retrying for that long automatically should have the same effect without the manual refresh.

Fix: extracted the retry-with-backoff loop out of `connectAvailable()` into a shared `connectWithRetries(mgr, usbId, firstDevice, onStatus)`, now used by *both* `scanDevices()` and `connectAvailable()` — `onStatus(label)` lets each caller show progress wherever makes sense (`scanDevices()` has no device card yet, so it updates the global status banner instead of a per-card status). Also widened `CONNECT_RETRY_DELAYS_MS` again, from `[1000, 2000, 3000, 5000, 8000]` (~19s) to `[1500, 3000, 5000, 8000, 12000, 15000]` (~44.5s, 7 total attempts) — closer to the real wall-clock time a manual hard-refresh-and-retry cycle was taking.

Also clarified for the user: `forgetDevice()`'s "Forget" and `showADBReleaseDialog()`'s "Release" are unrelated concepts that happen to share a word — `forget()` only revokes this browser's own WebUSB permission grant; the release dialog is about a *different* problem (something else on the OS holding the device open).

### v1.5.3 — widened retry window after a deep-dive into "Connection closed unexpectedly" / "device was disconnected"
Full investigation (2026-08-06) into the two USB connection failure messages that had been intermittently affecting one specific device (Zebra FR55, USB VID `0x05E0` PID `0x2106`) on one specific host, while another device (Zebra TC201, VID `0x05C6`) on the same host worked reliably:

- Ruled out: two-simultaneous-ADB-sessions contention (failed with `otherConnected=0` — the *other* device wasn't even connected).
- Ruled out: a full device-level lock or hardware fault — `chrome://usb-internals`'s own "Get Device Descriptor" test succeeded, returning a complete valid descriptor (manufacturer "Zebra Technologies", product "FR55", matching serial), and the ADB interface descriptor (Class 0xFF/Subclass 0x42/Protocol 0x01 — the standard ADB interface signature) looked normal.
- Notable finding: Windows Device Manager shows **CrowdStrike Device Control Sensor Interface** and **CrowdStrike Firmware Analysis Sensor Interface** installed on this host, and FR55 does not appear at all in Device Manager's "Devices by connection" tree (consistent with a filter/analysis driver intercepting it before normal PnP enumeration).
- Key data point that shaped the final theory: the *same* device, on the *same* host, sometimes connects successfully and sometimes doesn't — with the specific error varying between attempts. A hard, permanent policy block (e.g. CrowdStrike Device Control denying this VID outright) would fail identically every time regardless of retries; this intermittent, variable-duration pattern doesn't fit that.
- **Leading theory**: CrowdStrike's Firmware Analysis module briefly scans newly-attached/re-paired USB device firmware before releasing the device for normal OS/application use — a transient window of variable length, not a permanent deny. This is consistent with every observation: passive descriptor queries succeeding during the window, the device being invisible to normal PnP enumeration during it, TC201 (connected earlier, possibly already "trusted"/scanned) being unaffected, and a freshly-`forgetDevice()`'d-then-re-paired FR55 re-triggering a fresh scan (and thus the delay) each time.
- **Action taken**: widened `CONNECT_RETRY_DELAYS_MS` from `[1000, 2500, 4000]` (~7.5s total) to `[1000, 2000, 3000, 5000, 8000]` (~19s total, 6 attempts) — giving a potentially slower scan more room to finish before the app gives up. This is a workaround for a symptom, not a fix for the root cause.
- **If this theory is confirmed and the issue persists even with the wider window**: the actual fix is outside this app's control — it would need a CrowdStrike Falcon Device Control / Firmware Analysis policy exception for this device (VID `0x05E0`, PID `0x2106`) from IT/Security, since Falcon policy is managed centrally through the Falcon console, not locally.

All three places that build `.device-card` markup (connected, available, and the remote-viewer mirror in `renderMirrorDeviceList()`) needed updating together, since they all share the same CSS class.

### v1.4.4 — added: automatic retry for the "Connection closed unexpectedly" failure
Confirmed (2026-08-06, real hardware) this failure recurs even with the v1.4.3 400ms buffer between bulk connects, and even when the two devices are on physically separate USB ports (ruling out simple hub bandwidth contention as the sole cause). Root cause not fully understood — possibly host-controller/root-hub grouping behind the scenes even on "separate" ports, possibly endpoint security software, unconfirmed. Since the exact cause isn't nailed down, added a pragmatic mitigation: `connectAvailable()` now retries once automatically on failure, waiting 800ms and re-fetching a fresh device reference via `findGrantedDevice()` (a new shared helper) before retrying `connectDevice()` — WebUSB device references are transient, so retrying with the *same* object that just failed isn't reliable. If the retry also fails, the device is restored to "Ready to Connect" as before (v1.4.3). If this recurs even after the retry, the next step would be checking Windows Device Manager's "devices by connection" view to see if the two ports actually share a root hub, or checking for USB-filtering endpoint security software on the host.

### v1.4.3 — FIXED: bulk "Connect Selected" — a failed device vanished instead of returning to Ready to Connect
`connectDevice()` catches all its own errors internally (logs + status message) and never threw — so callers had no way to distinguish success from failure. Hit in practice with bulk-select: connecting two different physical devices back-to-back, the second failed with "Connection closed unexpectedly" (likely USB bus/hub contention from firing a second `connect()` immediately after the first succeeded) — `connectAvailable()` had already deleted it from `availableDevices` before attempting the connection, and since `connectDevice()` didn't signal failure, it never got restored. The device disappeared from both lists until an unrelated spontaneous `'connect'` event happened to trigger a rescan ~2s later — not a reliable recovery path.

Fix: `connectDevice()` now returns `true`/`false`. `connectAvailable()` checks this in both its instant-match and picker-fallback branches and restores the entry to `availableDevices` immediately on failure, instead of just for the outer picker-exception case it already handled. `connectSelected()` (the bulk action) also now waits 400ms between successive connect attempts, to reduce the chance of triggering the same bus contention in the first place.

### v1.4.2 — added: "Forget" button on Ready to Connect cards
Calls `USBDevice.forget()` (via `usbDevice.raw.forget()` on our wrapped type) to revoke this site's browser permission grant for that device, so it behaves like a never-paired device again (only reachable via the native picker from then on) — a UI way to simulate a fresh device connection instead of digging through Chrome's page-info → Site settings → USB devices. `forget()` isn't Baseline-supported across all browsers (works in Chrome); falls back to removing the entry from our own list only (with a clear debug-log warning that the browser-level grant wasn't actually revoked) if unsupported. Re-fetches a fresh device reference via `mgr.getDevices()` first if the stored entry's `usbDevice` is `null` (e.g. it arrived via `disconnectOne()`, which deliberately nulls that field per the "never cache usbDevice" convention).

### v1.4.2 — FIXED: freshly (re-)granted device showed in both Connected AND Ready to Connect
Race condition: `mgr.requestDevice()` granting a new permission fires the browser's native `'connect'` event essentially simultaneously with the picker flow's own direct `connectDevice(device)` call. That event's listener calls `scanAvailableDevices()` asynchronously — if it completed its "is this already in `connectedDevices`?" check *before* `connectDevice()`'s own (much longer) chain of awaits (`usbDevice.connect()`, `AdbDaemonTransport.authenticate()`, `adb.getProp('ro.serialno')`, ...) reached its `connectedDevices.set(...)` call, the scan would see `connectedDevices` still empty and add the device to `availableDevices` too — and nothing ever removed it afterward.

Also found while fixing this: `scanDevices()`'s own "already connected" duplicate-check had the same `.vendorId`/`.productId`-not-via-`.raw` bug as v1.3.2/v1.3.3, so it could never actually detect a duplicate.

Fix: `connectDevice()` now registers its target device's `vid:pid:serial` key in a module-level `connectingUsbIds` Set *synchronously*, before any `await`, and removes it in a `finally` block. `scanAvailableDevices()` skips any key present in that set (same treatment as "already connected"/"already available"). As a defensive backstop, `connectDevice()` also explicitly deletes any matching `availableDevices` entry right after adding to `connectedDevices`, in case some other race still slips one in. `scanDevices()`'s duplicate-check now reads `device.raw.vendorId`/`device.raw.productId` like everywhere else.

### v1.4.1 — FIXED: unplugging a never-connected "Ready to Connect" device did nothing
`navigator.usb.addEventListener('disconnect', ...)` was registered *lazily inside `connectDevice()`*, guarded by `if (!_usbDisconnectHandler)`. "Ready to Connect" entries are populated purely by `scanAvailableDevices()` (from a prior grant) and need no `connectDevice()` call at all — so on a fresh page load where the user hadn't yet clicked "Connect" on anything, no disconnect listener existed yet, and physically unplugging an available device did nothing; it stayed listed forever. Fix: the handler (now the standalone `handleUsbDisconnect()`, no longer an inline closure) is registered unconditionally at page-load time, next to the existing `'connect'` listener, both gated only by `!isViewerMode()`.

Also documented (not a bug, working as designed): WebUSB's permission model means `getDevices()` can only ever return devices already granted ("paired") to this origin. A never-granted device will only ever appear in the native `requestDevice()` picker (unpaired) — there's no API for a page to discover ungranted hardware, by deliberate design of the spec. To fully "un-pair"/simulate a fresh device: either revoke via Chrome's site settings (page-info icon → Site settings → USB devices), or call the granted device's underlying `USBDevice.forget()` (MDN-documented, Chrome-supported; via our wrapper this would be `usbDevice.raw.forget()`) — not currently wired into the UI as of v1.4.1.

### v1.3.2 — FIXED: "invalid USBDevice object — missing connect()" on Ready-to-Connect
This was actually the same root-cause class of bug as v1.1.41/v1.1.42 below, recurring because that earlier fix's "use `getDevices()`" was ambiguous about *which* `getDevices()`. `connectAvailable()` and `scanAvailableDevices()` were both calling `navigator.usb.getDevices()` — the plain native WebUSB API, which returns bare `USBDevice` objects. `.connect()` is **not** part of the WebUSB spec at all; it only exists on `AdbDaemonWebUsbDevice`, the wrapper type that `AdbDaemonWebUsbDeviceManager.BROWSER`'s own `requestDevice()`/`getDevices()` methods return. The "+Connect Device" button worked because `scanDevices()` already went through `mgr.requestDevice()` (wrapped); the "Ready to Connect" list's `connectAvailable()` went through the native, unwrapped `getDevices()` instead, so its found device lacked `.connect()` and tripped `connectDevice()`'s guard clause.

This same mismatch also explained a second symptom: a device already in `connectedDevices` (recorded via the wrapped `.serial`) kept reappearing as a duplicate "Ready to Connect" ghost entry with a fresh `vid:pid:timestamp` key on every scan — because the *old*, buggy `scanAvailableDevices()` computed its dedup key from the *native* device's `.serial` (empty/undefined for this hardware), which never matched the wrapped device's `.serial` the connected entry was keyed by.

Fix: both functions now call `AdbDaemonWebUsbDeviceManager.BROWSER.getDevices({filters:[AdbDefaultInterfaceFilter]})` instead of `navigator.usb.getDevices()`. Since `AdbDaemonWebUsbDevice` doesn't expose `vendorId`/`productId` directly (only via its `.raw` property, the underlying native `USBDevice`), all vid/pid comparisons in these two functions now go through `d.raw.vendorId`/`d.raw.productId` instead of `d.vendorId`/`d.productId`.

### v1.3.3 — FIXED: same bug, one more spot (`connectDevice()` itself)
The v1.3.2 fix above wasn't complete. `connectDevice(usbDevice)` — called from *both* the picker path and the reconnect path, always with a wrapped `AdbDaemonWebUsbDevice` — built its stored `_usbId` from `usbDevice.vendorId`/`usbDevice.productId` directly, which are `undefined` on the wrapped type (confirmed live: `connectDevice SUCCESS` logged `usb=undefined:undefined:253085251E0049`). That corrupted `_usbId` then propagated everywhere: `disconnectOne()` copies it verbatim into the "Ready to Connect" entry, so the *next* `connectAvailable()` call looks for `vid+pid=undefined:undefined`, never matches the real device (which has real numbers), and falls back to the native picker dialog every time instead of reconnecting instantly — and the stale duplicate "Ready to Connect" ghost entry persists for the same reason (dedup key mismatch against the corrupted connected entry). Fix: `connectDevice()` now reads `usbDevice.raw.vendorId`/`usbDevice.raw.productId` too, consistent with v1.3.2.

### v1.1.42 — FIXED
- `pipeTo` error: `connectAvailable()` was passing raw `USBDevice` to `AdbDaemonTransport.authenticate()` as `connection` parameter. Fix: use `getDevices()` + pass matching device to `connectDevice()` which handles `connect()` -> `USBConnection` properly.

### v1.1.41 — pipeTo error (superseded by 1.1.42)
- Attempted to fix by using `mgr.requestDevice()` from `connectAvailable()`. Still caused pipeTo error because `connectDevice()` expects a USBDevice it can call `.connect()` on, but the picker flow was not properly wired.

### v1.1.40 — disconnect handler key mismatch
- `disconnectOne()` moved device to availableDevices with key format `serial || vid:pid:timestamp`
- `scanAvailableDevices()` used `serial || vid:pid:timestamp`
- Mismatch caused duplicate entries. Fixed by aligning key formats.

### Historical patterns
- **WebUSB device references are transient**: `getDevices()` returns fresh objects each time. Never cache `usbDevice` across connections — always re-acquire via `getDevices()` or `requestDevice()`.
- **"`getDevices()`" is ambiguous — always mean `AdbDaemonWebUsbDeviceManager.BROWSER.getDevices()`**, never bare `navigator.usb.getDevices()`. Only the manager's version returns the wrapped `AdbDaemonWebUsbDevice` (with `.connect()`); the native one returns plain `USBDevice` objects that will fail `connectDevice()`'s guard clause. See v1.3.2 above — this exact ambiguity is what caused it to recur after v1.1.42.
- **ADB serial vs USB serial**: `adb.serial` comes from USB device, `ro.serialno` may differ. Always use `adbSerial` (from `ro.serialno` if available) as the Map key in `connectedDevices`.
- **Heartbeat must use ADB protocol, not raw USB**: `usbDevice.controlTransferOut` was unreliable. Current approach: `adb.getProp('ro.build.id')` with 1s timeout, 3s interval.

### Current disconnect handler issues
- Physical unplug detection relies on `navigator.usb.addEventListener('disconnect', ...)`. This fires reliably in Chrome/Edge.
- The handler matches by `_usbId.serial` first, then `vid+pid`. If two identical devices (same vid:pid, no serial) are present, matching may be ambiguous.
- After physical unplug, `scanAvailableDevices()` runs on the next USB connect event and may re-add devices. This is correct behavior — only re-adds if the device is physically present again.

## 10. Important Conventions

## 12. Remote Session (WebRTC sharing, + relay-based fallback)

Lets a second user (viewer), anywhere, with just a browser, join a session a host creates and run adb shell commands against the host's connected device (and, as of v1.14.0, request remote screen/input control — see below). Primarily peer-to-peer via WebRTC; signaling goes over a self-hosted relay we control (`relay-server/`, deployed on Render — see the debugging history below for why this replaced public Nostr relays). As of v1.10.0, the *actual session traffic* (not just signaling) also has a fallback path over that same relay, for networks where WebRTC's P2P/TURN mechanics are blocked outright (see "Relay-based fallback data path" below) — `makeRemoteActions()` sends every message over both paths transparently, so nothing above that layer needs to know which one actually delivered it.

### State
`remoteSession` (module-level, `src/index.js`) — either `null`, a host session (`{role:'host', room, roomId, password, viewers:Set, actions, control, pendingControlRequest}`), or a viewer session (`{role:'viewer', room, roomId, password, hostPeerId, actions, pendingRequests:Map, mirror:{activeSerial, connected[], available[]}, control}`). `actions` (both roles) is what `makeRemoteActions()` returns — see below, not just a thin wrapper over `room.makeAction()` anymore. There is no approval/trust gate for shell commands (removed in v1.13.0) — the share link itself is the authorization boundary. Screen/input control (v1.14.0) is the one exception: it does have a one-time, per-session Grant/Deny approval step (`control`/`pendingControlRequest` above), since granting live screen+touch access is a different order of trust decision than the shell access the link itself already implies.

### Relay-based fallback data path (v1.10.0, dedup fix + screen/input control v1.14.0)
`@trystero-p2p/ws-relay`'s server (`relay-server/node_modules/@trystero-p2p/ws-relay/dist/server.mjs`) is a generic topic-based pub/sub over plain WebSocket (`subscribe`/`unsubscribe`/`publish` to an arbitrary topic string) — nothing about it is WebRTC-signaling-specific. `createFallbackChannel(roomId, password, sessionId, label)` is a second, independent client speaking that same protocol on a room-scoped topic (`webadb-fallback-<roomId>`), carrying AES-GCM-encrypted (key derived from the room password) copies of the actual session messages. `makeRemoteActions(room, roomId, password, label)` wraps every action (`hello`/`devicePush`/`cmdRequest`/`cmdResponse`/`pathComplete`/`pathCompleteResult`/`tabDataPush`/`bye`/`controlRequest`/`controlResponse`/`controlRelease`/`controlRevoked`/`screenFrame`/`inputEvent`/`orientationStatus`/`apkTransferStart`/`apkTransferChunk`/`apkTransferEnd`/`apkInstallResult`/`screenshotRequest`/`screenshotResult`) so `send()` goes out over both the real P2P channel (best-effort — silently a no-op if trystero doesn't recognize the target, same as its own behavior for an inactive peer) and the fallback channel, and both transports funnel into one internal `deliver()` that dedups by `action:requestId` for message types that carry one (tightened in v1.14.0 from "fallback-side dedup only" to "both transports funnel through one dedup gate" — see below). Every caller elsewhere in the file is unaware this exists — they only ever see `{send, onMessage}` and a `ctx.peerId`, which is now either a real trystero peerId or (fallback-only) the sender's random session UUID.

**`screenFrame`/`inputEvent` were briefly P2P-only** (v1.14.0 initial ship), skipping the fallback send above, on the theory that they're high-frequency and a WS-relay round trip would be too slow to make remote control usable anyway. Reverted the same day after real-world testing: a viewer whose network doesn't establish real P2P at all (the same class of restriction that motivated this whole fallback channel) saw the Grant/Deny handshake work fine (dual-transport) but the screen stayed a broken image forever — no frame or tap ever got through, since both of those actions were P2P-only and P2P silently never connected. Reliability on the networks this app actually gets used on beats the relay-load savings; the `grantId`+`seq` scoping (see below) already makes the resulting cross-transport reordering/double-delivery harmless, so there's no correctness cost to sending these over both transports too.

This exists because some networks (confirmed: Zscaler-proxied corporate networks) don't just have a flaky TURN server — they break WebRTC's ICE/TURN mechanics at the network level, so no amount of TURN-provider-swapping fixes it. The relay's plain WSS connection is the one thing that's worked in every diagnostic capture throughout this investigation, so it became the answer once it was clear the problem wasn't fixable by treating it as "which TURN provider" (see `TURN_RELIABILITY_ANALYSIS.md`, untracked in repo root, for the full diagnostic trail that led here).

### Host flow
1. `startShareSession()` — generates roomId/password (`crypto.getRandomValues`), joins a trystero room, wires up actions, shows the share modal (`showShareModal()`, built at runtime like `showDevicePicker()`).
2. `renderDeviceList()` has a single hook (`if (remoteSession?.role === 'host') broadcastDeviceState();`) that pushes a serializable device snapshot to all viewers on every state change — this is what keeps requirement "viewer sees live connect/disconnect" in sync, without touching every call site.
3. Incoming `cmdRequest` from a viewer → `handleRemoteCmdRequest()` → `executeRemoteShell()` directly and unconditionally (no approval gate — see v1.13.0), which calls the **same unmodified `adbShell()`** used by the local `runShell()` — no duplicated shell logic.

### Viewer flow
1. A link `#room=<id>&key=<password>` — the URL fragment is never sent to any server. `initRemoteViewerIfLinked()` (called from `init()`) detects it and calls `joinAsViewer()`, which skips WebUSB entirely (`isViewerMode()` guards the page-load `scanAvailableDevices()` call and the `navigator.usb` `connect` listener).
2. `renderMirrorDeviceList()` mirrors the host's device list into the same `#device-list`/`#welcome-msg` sidebar elements the host UI uses (read-only, no connect/disconnect buttons) — reuses existing CSS rather than a parallel UI.
3. Viewer mode reuses the host's full `#inspector-section` tab bar (v1.11.0) rather than a separate panel; the `.viewer-only` block inside `#tab-shell` is the remote-shell UI — `sendRemoteCommand()` sends a `cmdRequest` to the host and `handleCmdResponse()` renders the result, which now comes back immediately (no approval step).
4. All three inbound viewer listeners (`devicePush`, `cmdResponse`, `bye`) check `ctx.peerId === remoteSession.hostPeerId` before acting — without that, a second peer in the same room could spoof messages to another viewer (trystero has no built-in sender-role enforcement).

### Screen/Input Remote Control (v1.14.0, per-device rework v1.16.0)
Vysor-style remote control: a viewer can request to see the host's device screen and send taps/swipes/text/hardware-key presses, which the host injects via `adb shell input ...`. **Control is per-device, not per-session** (reworked v1.16.0): each connected device has its own independent control instance — two different viewers can hold control of two different devices at once, but a given device can only ever have one controller at a time (a request for an already-controlled device is auto-denied). Screen frames are sent only to a device's current controller, never broadcast to other viewers.

- **Dispatch-dedup prerequisite fix**: before this feature, `makeRemoteActions()`'s dual-transport wrapper delivered every message via both the real P2P path and the fallback WS-relay path *independently* — when both transports were healthy (the common case), every message could be handled twice, under two different `ctx.peerId` values for the same sender (real trystero peerId vs. the fallback's per-tab session UUID). Harmless for old idempotent actions, but would have broken a stateful control system and made `inputEvent` (fire-and-forget, no natural idempotency) cause literal double-taps/double-swipes. Fixed by funneling both transports through one internal `deliver(name, data, ctx)` that dedups by `(action, requestId)` regardless of which transport won, and by setting `real.onMessage` exactly once at action creation (callers now only ever touch the `dispatchers` map, never `real.onMessage` directly — this also structurally rules out ever repeating the v1.10.x getter/setter-mismatch bug).
- **`grantId` + `seq` scoping**: `screenFrame` and `inputEvent` are high-frequency and not naturally request/response-shaped, so they're excluded from the requestId-based dedup above and instead carry their own ordering guard, plus a `serial` field (since there can be more than one control session live at once). `grantId` (a `crypto.randomUUID()` the host mints at grant time) scopes every message belonging to one device's control session end-to-end — both sides drop anything whose `grantId` doesn't match that device's current session, which fully eliminates cross-session bleed (e.g. a frame captured just before revoke arriving after a *new*, different grant for the same device has already started). `seq` (monotonic per grantId) additionally orders frames/input events within one session so a reordered delivery can't cause a visible rewind or a duplicate input action.
- **Dual-transport, adaptively** (tuned v1.16.0): `screenFrame`/`inputEvent` are sent over the fallback relay too (needed — a P2P-less viewer's screen was permanently broken when these were P2P-only), but `wrap()`'s `send()` skips the fallback send for these two specifically when `room.getPeers()[opts.target]` shows an already-live P2P connection to that exact target — the fallback path's `encryptForFallback()` (JSON.stringify → AES-GCM → JSON.stringify the ciphertext as a number array) is real, payload-size-scaling, synchronous main-thread work, and paying it on every frame even when P2P works fine was directly hurting fps. Falls back to the relay only for a target with no active P2P entry.
- **Binary-safe capture**: `adbScreencap(adb, timeoutMs)` mirrors `adbShellTimed()`'s `AbortController`+`process.kill()` pattern but pipes through `ConcatBufferStream` (not `TextDecoderStream`) to get raw PNG bytes — the existing `adbShell`/`adbShellTimed` are both text-decoded and would corrupt binary image data. `captureScaledFrame(adb, maxWidth, jpegQuality)` decodes that PNG via `createImageBitmap`, scales it down onto an `OffscreenCanvas` (currently 360px wide, quality 0.45 — tuned down from an initial 480px/0.55 for speed) and re-encodes as JPEG before base64-encoding (`uint8ToBase64()`, chunked to avoid a stack overflow on `String.fromCharCode`). The real (pre-scale) device resolution is returned alongside so the viewer can map tap/swipe coordinates from the smaller transmitted image back to real device pixels.
- **State (per-device, v1.16.0)**: host has `remoteSession.controlBySerial: Map<serial, {peerId, grantId, seq, lastInputSeq}>` and `remoteSession.controlRequestQueue: [{peerId, serial, requestId}, ...]` (a queue — more than one simultaneous request, for different devices, is now a real possibility; reviewed one at a time via a single reused Grant/Deny modal that auto-advances to the next queued request). Viewer has `remoteSession.controlBySerial: {serial: {active, grantId, lastAppliedSeq, inputSeq, lastFrameW, lastFrameH, lastJpeg}}` — `lastJpeg` caches the most recent frame per device so switching back to an already-controlled device shows it immediately instead of waiting for the next poll.
- **Host flow**: `handleControlRequest()` → queues (or immediately re-confirms/denies) → `showControlRequestPrompt()` (an overlay+box modal built at runtime, same pattern as `showShareModal()`, showing queue[0] plus a "N more waiting" note) → `grantControlRequest()`/`denyControlRequest()` (act on `queue.shift()`, then re-show the prompt if more are queued). Granting starts `startScreencapLoop(peerId, serial, grantId)`, a recursive `setTimeout` (not `setInterval`, so a slow capture never overlaps the next one; 15ms gap, tuned down from an original 250ms fixed floor that was pure dead time on top of the actual on-device capture cost — see v1.15.0 changelog) that re-checks `controlBySerial.get(serial)`'s `grantId` on both sides of each async capture, so a revoke mid-capture just stops that device's loop rescheduling itself rather than sending a stale frame into a new session. `handleInputEvent()` dispatches by `type` to plain `adbShell()` calls (`input tap/swipe/keyevent/text`) — `toSafeInt()` coerces all numeric fields before they're interpolated into the shell command string, since these values are otherwise attacker-controllable-in-principle even from an already-granted session. `showControlActiveBanner()` is a full re-render of `#control-active-banner` from `controlBySerial` — one row per currently-controlled device (plural now possible), each with its own Stop button.
- **Cleanup**: `notifyDeviceRemoved(serial)` is called from all six independent `connectedDevices.delete(...)` call sites (`handleUsbError`, the USB-disconnect-event matcher, the `connection.closed` handler, the heartbeat-failure handler, `disconnectOne`, `disconnectDevice`) so a device going away always tears down any control session or pending request tied to that specific serial, regardless of which of the six paths triggered the removal. `handlePeerLeaveHost()` sweeps `controlBySerial` for any entries owned by the departing peer (there can be more than one, if that viewer somehow held control of multiple devices) and filters that peer out of `controlRequestQueue`; `stopShareSession()` hides both control UI elements defensively on teardown.
- **Viewer UI**: a "Remote Control" tab, reachable only by viewers. Per a CSS-specificity check done before implementing: `.viewer-only` must **not** be applied to a `.tab-content` element, since `#inspector-section.viewer-mode .viewer-only { display:block }` (ID + 2 classes) beats `.tab-content.active { display:block }` (2 classes) and would force the tab visible regardless of which tab is actually selected. Only the tab-bar **button** (`#tab-btn-control`) gets `.viewer-only`; the tab-content (`#tab-control`) is a completely ordinary tab, unreachable by a host simply because its button doesn't exist for them. `renderControlTab()` is the single function that redraws the whole tab from whatever's true for `mirror.activeSerial`'s own `controlBySerial` entry — called from `setMirrorActiveSerial()` on every device switch (so each device's Request/In-control/screen state shows correctly and independently) and from `handleControlResponse()`/`handleControlRevoked()` when a grant/revoke affects the currently-*displayed* device specifically. `handleScreenFrame()` updates the `<img>` directly rather than going through a full re-render, since it fires several times a second.
- **A real bug this design fixed in passing**: `handleViewerHello()`'s tab-data catch-up dump used to be *targeted* (`{target: peerId}`), which is fragile in exactly the way the state above is designed to avoid — see the v1.16.0 changelog entry for the "every tab shows Waiting for host data" root cause (a targeted send only reaches a viewer over the transport whose own identity happens to match `target`; the other transport's own check silently drops it). Fixed by broadcasting that specific dump instead. Worth remembering for any *new* one-off targeted send that isn't naturally a request/response reply (replies are safe because they reuse the exact `ctx.peerId` the request arrived with, so request and reply always agree on which transport-identity to use even though the value itself varies per message).
- **Extra capabilities bundled into the same control grant, no separate approval (v1.21.0)**: screen rotation (`queryOrientation()`/`setOrientation()`, `orientationStatus` action), full-resolution screenshot (`screenshotRequest`/`screenshotResult`, v1.22.0 — separate from the scaled-down `screenFrame` stream, downloaded via a synthetic `<a download>` click), and APK install (`apkTransferStart`/`Chunk`/`End` + `apkInstallResult`, pushed via `adb.sync().write()` then `pm install -r`) are all gated by the SAME check every input event already uses (`entry.peerId === peerId && entry.grantId === grantId`) rather than a second Grant/Deny prompt — granting screen/input control is treated as sufficient authorization for these too, since they're just more powerful forms of the same "you can drive this device" trust the viewer already has. `queryOrientation()`'s read side uses `settings get system accelerometer_rotation`/`user_rotation` (fixed v1.22.0 — the original `wm user-rotation`-output-parsing approach never actually matched real device output); the write side still uses `wm user-rotation lock N`/`free` per the user's explicit ask. See the v1.21.0/v1.22.0 changelog entries for the full design (chunking, idempotent chunk application, why `adb.sync()` is the right tool here unlike `readDeviceFile()`'s deliberate shell-only approach for small reads).

### Known limitations (v1) / debugging history
- `REMOTE_TURN_CONFIG` (near `remoteSession` state) wires in the free/shared Open Relay Project TURN servers (incl. a 443/TCP option) as a fallback when direct STUN-only P2P fails. Open Relay's servers are free/shared and rate-limited — fine for personal/team use, not a production SLA.
- **Cross-network debugging saga (2026-08-04) — root cause: relay overlap, not a firewall block.** A host on a corporate network repeatedly showed zero `WebRTC peer joined` events while two independent remote viewers instead found *each other* (trystero rooms are a full mesh). Investigation went through several wrong turns before landing on the real cause:
  1. First hypothesis: corporate web filter blocking Nostr relay signaling outright. Pinned `relayConfig` to 4 well-known relays (`relay.damus.io`, `nos.lol`, `relay.nostr.band`, `relay.snort.social`) to test this.
  2. That surfaced a *different* problem: a plain `wss://echo.websocket.org` test proved WebSocket itself was never blocked, and the console showed `Trystero: relay failure from wss://relay.damus.io/ - rate-limited` — our own repeated test cycles had concentrated load onto just 4 relays and tripped their abuse protection. Reverted the pin back to the library default (5 random relays from its ~47-relay pool per `joinRoom()` call) to stop self-inflicting rate limits.
  3. That reverted default then failed *identically on both host and viewer* — both consoles showed `WebSocket connection to 'wss://relay.nostrdice.com/' failed` and `wss://hol.is` failed. Same two dead relays on two unrelated networks meant those two relays were just down/unreliable — not a client-side or firewall issue.
  4. The actual root cause: `joinRoom()`'s default behavior has each side **independently** pick 5 random relays out of the 47-relay pool. For two peers to find each other they need at least one relay in common — with independent random 5-of-47 draws, there's roughly a 50%+ chance of *zero* overlap between host and viewer on any given attempt. That fully explains the inconsistent behavior throughout this investigation.
  - **Fix**: `REMOTE_RELAY_URLS` pins both host and viewer to the same fixed list of 8 relays across different operators (`relay.damus.io`, `nos.lol`, `relay.nostr.band`, `relay.snort.social`, `relay.primal.net`, `purplerelay.com`, `communities.nos.social`, `relay.mostr.pub`) with `redundancy` set to try all 8 — guaranteeing overlap (same list on both sides) while being large enough that 2-3 flaky/rate-limited relays don't matter. `warnOnRelayFailure: true` stays on so relay-level issues keep surfacing in the console.
- Lesson for future debugging here: a "stuck connecting" / "0 peers joined" symptom is NOT reliable evidence of a firewall block by itself — check the browser console for explicit relay-level messages (`rate-limited`, `failed`) on *both* sides before assuming network-level blocking, and avoid rapid repeated `joinRoom()` test cycles against a small relay set (self-inflicted rate-limiting looks identical to a real block from the app's own logs).
- There is no per-command approval gate (removed in v1.13.0) — any peer in the room can run commands on the host's connected device the moment they join. The share link is the only access control; treat it like a password.
- Viewer mirror covers the device list, shell, and Properties/Features/Packages/Attestation/RKP tabs. As of v1.19.0, all five tabs are proactively fetched (`prefetchTabsForViewers()`) for every connected device the host *hasn't* personally clicked, the moment a share session is active — no tab requires an actual host visit anymore for a viewer to see it (accepted cost: a real per-device delay, since RKP alone runs a dozen-plus ADB round trips). As of v1.18.0, `startShareSession()` also explicitly re-broadcasts `activeSerial`'s own already-rendered tabs the moment sharing starts — needed because `pushTabHtml()` silently no-ops whenever `remoteSession` doesn't exist yet, which it never does at the moment a device auto-selects itself on connect, before the host has clicked Share.
- **Final resolution (2026-08-04): switched off public Nostr relays entirely, to a self-hosted signaling relay.** After the relay-pinning fix still failed cross-network testing (confirmed via `pollIceState()` diagnostic — zero `RTCPeerConnection` objects were ever created on either side, ruling out ICE/TURN and pointing squarely at signaling never succeeding — plus a renewed `rate-limited` message from `relay.damus.io`, meaning even the pinned 8-relay list was degraded from cumulative testing), the decision was to self-host: `relay-server/` is a small Node service using `@trystero-p2p/ws-relay`'s server helper (`createWsRelayServer`), deployed on Render.com's free tier at `wss://web-adb-inspector-relay.onrender.com`. The client (`src/index.js`) now imports from `@trystero-p2p/ws-relay` instead of `@trystero-p2p/nostr`, with `REMOTE_RELAY_URLS` pointing at that single URL. This removes rate-limiting, relay-overlap odds, and third-party downtime as failure modes entirely — the relay is dedicated to just this app.
  - **Real bug hit and fixed during this build**: `createWsRelayServer(options)` destructures as `const {onError, ...wsOptions} = options`, spreading the *rest* directly into `new WebSocketServer(...)`. So `server`/`port` must be top-level keys in the options object passed to `createWsRelayServer()` — nesting them under a `wsOptions: {...}` sub-key (an easy mistake to make from the API's internal variable name) silently creates an unrelated default WebSocketServer on port 8080 instead of attaching to the intended HTTP server. Caught via a local smoke test (HTTP health check succeeded, but a real WebSocket client got "Unexpected server response: 200" instead of a 101 upgrade) — see `relay-server/server.js` for the fixed version and the comment explaining it.
  - Render free tier spins down after 15 min idle (~30-50s cold-start on the next connection) — a known, accepted tradeoff for zero-cost hosting.
  - **Debugging tool note**: don't use bare Node.js (`node -e` scripts, etc.) to test HTTPS/WSS connectivity from a corporate-network machine as a proxy for what the browser will experience — Node bundles its own CA list and does NOT read the OS/browser certificate store, so it can fail TLS validation (`unable to get local issuer certificate`) against a corporate TLS-inspecting proxy even when the actual browser (which does trust the OS cert store, like PowerShell's `Invoke-WebRequest`) would succeed fine. This produced a red-herring failure while validating the Render deployment.
